# Native history import

Run on the source machine, at its original current daemon paths, against the hub:

```sh
bun scripts/history/run.ts --manifest /outside/repo/pinned-native.json --epoch-bytes 1073741824
```

The default run verifies the first source's pinned first 32 records, accepts its `FINAL` coverage, then continues the entire supplied queue in autonomous epochs. `--pilot-only` exits after acceptance. No mtime filter or global 32-record limit applies. This command never runs from `--backfill`; that runner retains its 35 GiB floor.

The JSON manifest has `machine` (equal to `TOKENLAYER_MACHINE`) and ordered `sources`. Each source has `path` (absolute physical original path), `kind`, `sessionId`, `physicalSha256`, `decodedSha256`, `decodedBytes`, `prefixBytes`, `prefixSha256`. The first source's prefix must contain exactly 32 complete nonempty LF records. Plain/zstd twins have one logical identity: select the plain representation when both exist. Native Codex header UUID and filename must agree. Claude session IDs and Antigravity directory IDs are checked. Pins must come from source-side reads; metadata or a copied filename alone does not prove origin.

Use the current-root, never-shipped queue selected by the source inventory, with no date cutoff. Supported CLI roots match daemon Claude, Codex, Antigravity CLI and T3 Antigravity env settings. A manifest has at most 4,096 sources and 16 MiB of metadata; a source at most 64 GiB decoded and a record defaults to at most 1 MiB of non-LF bytes (CR counts). The importer alone accepts `--max-record-bytes 16777216` to opt into a maximum of 16 MiB; the same validated option reaches source verification, plain/zstd inspection and the tail reader. No daemon flag or environment setting enables the larger cap. Records above the selected cap stop the queue; no truncation, skip or quarantine occurs. Kiro, Gemini JSON, SQLite exports, moved roots, tar and Drive need their separate adapter/ownership slices. They are not queue completion claims here.

State is private under `~/.config/tokenlayer/history-import/<manifest-sha256>/`: independent progress/generation files, an fsynced intent/acked/ambiguous NDJSON ledger, and epoch receipts including before/after `FINAL` matrices. No payload is spooled. Live ship/backfill lineage is read only. Conflicting lineage or same-native ownership/hash overlap at another replacement identity stops admission for reconciliation. Exact existing keys are reused; repeated lines at different offsets remain events. Arbitrary cross-copy occurrence mapping is deferred.

Each epoch defaults to 1 GiB (512 MiB–1 GiB accepted). It reserves 384 MiB for scratch/state/overhead and charges exact JSONEachRow payload bytes plus 4× storage/merge allowance, cumulatively. Each insert re-queries free/unreserved space, retaining the installed 15 GiB reserve and another 2 GiB margin. Unknown/stale data, source mutation, unresolved ownership, insert errors, state caps and signals stop admission. One dispatched batch may finish. The 4× allowance is a conservative bound for this slice, not a universal measured amplification guarantee; independent writers still consume space.

Unacknowledged intent is re-queried by exact native keys on the next run: full coverage becomes acked, zero becomes retryable, partial/torn ledger stops for reconciliation. No automatic HTTP retry occurs. A writer lock prevents concurrent importer runs; SIGKILL leaves the lock as a technical stop. Inspect its PID/start/manifest and verify the previous writer is absent before an owner removes that exact lock; the importer never reaps it. Resume with the same manifest and retained state. Never remove live checkpoints or source/archive files.

Epoch matrices use provider harness and raw event month, including `197001`; that bucket can contain missing, invalid or explicit epoch dates. Dates and proxy fields are never manufactured. This slice does no schema migration, service restart, source deletion, archive download or `proxy_usage` write.

Revision R1 bounds coverage tuples and overlap session/hash lists by escaped UTF-8 SQL bytes (48 KiB per list, 192 KiB per query before the format suffix). Importer batches also split at 4,096 nonempty records, preserving intervening blank bytes and offsets in plain and zstd sources. Unset daemon options keep their existing batches. Server query limits are unchanged. Single keys too large for this bound stop locally.

Active progress is bounded per current source plus pilot lineage and the in-flight ledger (64 MiB); active epoch receipts have a separate 16 MiB segment cap. Full record audit is retained without a cumulative manifest-size cap. `audit/ledger.<uuid>.ndjson` and `audit/receipts.<uuid>.ndjson` are immutable completed segments; completed per-source checkpoint files also remain for replay/lineage. All segments plus the current files form the audit trail. They still consume physical disk and can cause the existing space guard to stop admission.

Rotation fsyncs the replacement, hard-links the old log into the private audit directory, fsyncs that directory, then atomically replaces the active file and fsyncs its parent. Pending intents are retained in the replacement before reconciliation writes an ack/retry. A crash before replacement leaves a shared old inode: startup detects it and rotates again before appending, preserving the archived bytes. This requires local filesystem hard-link and atomic-rename support; errors stop admission. Terminal history from older cumulative ledgers is streamed into audit rotation instead of being rejected by total size. A torn ledger or receipt still needs manual reconciliation; it is never discarded. No automatic audit deletion occurs.

On each execution, intent reconciliation precedes resetting the importer's generation journal to its acknowledged checkpoint. This avoids replaying an acknowledged prefix after ordinary failures. Every completed source must match its verified nonempty LF-record count in FINAL, and blank-only LF batches advance the decoded checkpoint without event inserts. Epoch exhaustion receipts use `epoch-rollover`.

N4 follow-up discovers owners freshly once per escaped 48 KiB owner chunk per batch. It unions at most 4,096 explicit `(machine,path)` tuples and 2 MiB of escaped tuples, then checks each bounded path/hash combination. Empty owner sets skip hash checks; no owner cache survives the batch. Owner scans use `max_execution_time=20,max_threads=2,max_memory_usage=536870912,max_result_rows=4096,max_result_bytes=2097152,result_overflow_mode='throw'`. FINAL matrices retain their 30-second/4,096-row limits and also use 2 threads and 512 MiB. Any query/union/overlap refusal stops before intent/insert; no server settings change.

N9 checks the local state volume using synchronous `statfs` `bavail × bsize` (BigInt), preserving **20 GiB** plus bounded pending allocation before importer writes. This is the documented M4 local-state floor, independent of the hub's unchanged 15 GiB reserve and 2 GiB margin. Purgeable/reclaimable capacity is never credited. Unknown statistics or filesystem errors fail closed. Directory/lock/log/checkpoint writes refresh the check; ledger admission additionally budgets four serialized intent records plus 1 KiB, two maximum 64 MiB checkpoint replacements and one 16 MiB receipt segment (at most 208 MiB). Each individual write includes 4 KiB metadata allowance; any requested pending allocation over 272 MiB refuses. Rotation checks replacement bytes before creating audit/replacement files. Checkpoint writes use the guarded writer only for this importer; default daemon/manual state writing is unchanged. Legacy importer checkpoint versions require reconciliation instead of an unguarded upgrade.

This is admission accounting, not an OS reservation: other writers can consume space after a check. A mid-insert local-space drop may retain an unresolved intent and prevent ack/checkpoint/stop-receipt writes; resume only after capacity is restored and reconcile. Audit remains cumulative and is never deleted. A low/unknown-space refusal can therefore have no new local receipt; the CLI error is the stop evidence. The programmatic `localSpace` statistic-reader injection is for throwaway tests, with no CLI/env floor override.

Conservative holds: N5: no skip/quarantine; unresolved ownership halts the manifest. N7: roots must be canonical, nonsymlink paths (the shipper's lexical pickup must equal the verified allowlist). N8: resumed/forked Claude copies may stop on overlap; occurrence mapping remains a separate slice. N4/N9 changes require their own Claude approval and merge before autonomous queue use. No production cost or lifetime completeness is measured here.


Large-record admission keeps one in-flight batch, at most 4,096 event rows, and the existing line-boundary byte windows. Programmatic importer `batchBytes` is now explicitly limited to 1 byte–4 MiB (default 256 KiB). A single complete record may exceed that window, up to the selected record cap plus LF. Plain reads allocate at most max(window, record cap + LF); zstd retains at most the window plus one record plus a 256 KiB decoder block. The PR92 first-record window is retained through the complete first LF record, bounded by the selected cap plus LF, rather than retaining a whole decoded file.

Before token hashing or encoding, scalar row sizes are counted without constructing a large JSON string. Both token JSON and exact byte-preserving JSONEachRow payload are independently limited to 128 MiB; raw control-byte escaping is counted exactly before payload allocation. Tool arguments/content stay within their source record cap. The exact payload is still charged fivefold: `384 MiB + 5 * payloadBytes` cumulatively per epoch. Thus a fresh 1 GiB epoch admits at most 128 MiB of payload, and a fresh 512 MiB epoch at most floor(128 MiB / 5) = 26,843,545 bytes. A single batch that cannot fit an empty epoch stops instead of looping or increasing caps. The 384 MiB base is conservative admission accounting, not a measured RAM guarantee. Bounded strings, parsing and encoder copies can coexist; process peak memory depends on JSON escaping and the runtime.

Large raw records never enter the intent ledger or checkpoints: those retain keys, hashes, offsets and parser metadata. The unchanged 64 MiB active-state cap, four-intent reserve, two 64 MiB checkpoint replacements, 16 MiB receipt segment and 272 MiB pending-allocation refusal still apply. Maximum ledger admission pending remains 208 MiB before per-write 4 KiB metadata checks; local free-space floor stays 20 GiB. Hub reserve accounting remains 15 GiB plus 2 GiB margin. Decoder cleanup preserves a primary record-cap error; a naturally failing decoder remains a distinct decode error. External source pin-builder changes are owner-applied companion patches, not part of daemon deployment.
